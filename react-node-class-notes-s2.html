classList — Dark / Light Mode Toggle
header.jsx · index.css · document.body

Before adding React state or any library, you used a raw browser API: document.body.classList. Every HTML element has a classList property that lets you add, remove, or toggle CSS class names from JavaScript. You applied this directly inside a React event handler — proving that React doesn't replace the DOM, it sits on top of it.

The three methods you covered:

concept — the three classList methods
// .add() — adds a class (even if already present, no duplicate)
document.body.classList.add('dark')      // body now has class="dark"

// .remove() — removes a class (safe even if class isn't there)
document.body.classList.remove('dark')   // body now has class=""

// .toggle() — adds if not present, removes if present
// This is what you used in the project — one function does both
document.body.classList.toggle('dark')   // flips between dark / not dark
index.css — the dark class that gets toggled
.dark {
  background-color: #222;
  color: white;
}
a {
  color: #8ab4f8;
}
header.jsx — togglemode function + button
function Header({setsearchquery}) {

  // Pure DOM function — no React state needed here
  function togglemode() {
    document.body.classList.toggle('dark')
    // First click: adds 'dark' → body turns dark background, white text
    // Second click: removes 'dark' → body goes back to default
    // Every click after: keeps flipping
  }

  return (
    <header>
      {/* ... logo, input, nav ... */}
      <button onClick={togglemode}>dark/light</button>
    </header>
  )
}
Why no useState here? You don't need to store "is dark mode on" in React state because the CSS class on document.body IS the source of truth. The browser remembers it. React re-renders only when its own state/props change — this button triggers a DOM change directly, which is perfectly valid for simple global UI toggles.
The flow:
Button click
→
onClick fires togglemode()
→
classList.toggle('dark')
→
CSS .dark rule applies to entire page

Array.filter() — Live Product Search
Products.jsx · header.jsx · App.jsx

You implemented live search across the entire app — as the user types in the Header input, the Products grid filters in real time. This required connecting three components using state lifting: the search state lives in App.jsx (the common ancestor), gets sent down to Header as the setter, and to Products as the query value.

The actual filtering uses Array.filter() — a built-in JavaScript method that returns a new array containing only elements where your callback function returns true. Combined with .toLowerCase() and .includes(), you get case-insensitive substring matching.

concept — how Array.filter() works
// filter() loops through every item in the array
// keeps only items where the callback returns true
// returns a BRAND NEW array — original is not changed

const nums = [1, 2, 3, 4, 5]
const evens = nums.filter((n) => n % 2 === 0)   // [2, 4]

// Same idea — filter products where title contains the search query
const results = products.filter((p) => {
  return p.title.toLowerCase().includes(query.toLowerCase())
  // .toLowerCase() on BOTH sides → case-insensitive match
  // .includes() → true if query appears anywhere in title
})
App.jsx — searchquery state lifted here, passed down both ways
import { useState } from 'react'
import Header   from './header'
import Products from './Products'

function App() {
  const [searchquery, setsearchquery] = useState('')
  // searchquery lives HERE (common ancestor of Header + Products)

  return (
    <>
      <Header  setsearchquery={setsearchquery}  />
      {/* Header gets the SETTER — it calls it when user types */}

      <Products  searchquery={searchquery}  />
      {/* Products gets the VALUE — it uses it to filter */}
    </>
  )
}
header.jsx — receives setsearchquery as prop, calls it on change
function Header({ setsearchquery }) {
  return (
    <input
      onChange={(e) => { setsearchquery(e.target.value) }}
      placeholder="search the products..."
      type="text"
    />
  )
}
Products.jsx — receives searchquery, runs filter, maps filteredproducts
function Products({ searchquery }) {
  const [products, setproducts] = useState([])

  useEffect(() => {
    fetch('http://localhost:3000/products')
      .then(r => r.json())
      .then(data => setproducts(data))
  }, [])

  // filter runs on every render — whenever searchquery changes,
  // App re-renders Products with the new value, filter runs again
  let filteredproducts = products.filter((p) => {
    return p.title.toLowerCase().includes(searchquery.toLowerCase())
  })

  return (
    <>
      {filteredproducts.map((e) =>
        <Card image={e.image} title={e.title} price={e.price} />
      )}
    </>
  )
}
State lifting explained: Header and Products don't talk to each other directly — they're siblings. React data only flows downward (parent → child). So when two siblings need to share state, you "lift" the state up to their closest common parent — here that's App.jsx. App stores the query, gives the setter to Header, gives the value to Products. This is one of the most important React patterns.
Why not just filter inside useEffect? Because useEffect only runs when dependencies change. The filtering needs to happen on every keystroke — that's a render-time operation, not a side effect. So you filter synchronously during render, not inside useEffect.

React Router DOM — Full Client-Side Routing
main.jsx · App.jsx · header.jsx

By default, React is a Single Page Application — there is literally one HTML file (index.html) and React swaps content in and out without the browser ever navigating to a new page. React Router DOM is the library that makes URLs feel like they navigate to different pages, while staying inside that single HTML file the whole time. No full page reload ever happens.

The setup requires three pieces working together: BrowserRouter wraps the whole app in main.jsx, Routes and Route define which component shows at which URL path in App.jsx, and Link replaces <a href> tags in header.jsx for navigation without page reloads.

main.jsx — BrowserRouter wraps everything at the top level
import { BrowserRouter } from 'react-router-dom'
import App from './App.jsx'

createRoot(document.getElementById('root')).render(
  <BrowserRouter>         ← must wrap App, not the other way around
    <StrictMode>
      <App />
    </StrictMode>
  </BrowserRouter>
)
App.jsx — Routes and Route define the URL → component map
import { Route, Routes } from 'react-router-dom'
import Header   from './header'
import Products from './Products'
import About    from './About'
import Signup   from './Signup'
import Signin   from './Signin'

function App() {
  const [searchquery, setsearchquery] = useState('')

  return (
    <>
      <Header setsearchquery={setsearchquery} />
      // Header always shows on every page — it's OUTSIDE Routes

      <Routes>
        // Each Route maps a URL path to a component
        <Route path='/'         element={<Products searchquery={searchquery} />} />
        <Route path='/about'    element={<About />}                          />
        <Route path='/products' element={<Products searchquery={searchquery} />} />
        <Route path='/register' element={<Signup />}                          />
        <Route path='/login'    element={<Signin />}                          />
      </Routes>
    </>
  )
}
header.jsx — Link replaces <a href> for SPA navigation
import { Link } from "react-router-dom"

<nav style={{display:"flex", gap:"10px"}}>
  <Link to='/'>       <a>HOME</a>     </Link>
  <Link to='/about'>   <a>ABOUT</a>    </Link>
  <Link to='/products'> <a>PRODUCTS</a> </Link>
  <Link to='/register'> <a>SIGNUP</a>   </Link>
  <Link to='/login'>    <a>SIGNIN</a>   </Link>
</nav>
Why Link and not <a href="">? A regular <a href="/about"> causes a full browser page reload — the entire React app is thrown away and re-downloaded. <Link to="/about"> intercepts the click, updates the URL bar using the History API, and tells React Router to swap the component — all without touching the server. That's the entire SPA advantage: instant navigation, state preserved, no flash.
Why is Header outside <Routes>? Anything outside <Routes> renders on every page. The header, footer, sidebar — all persistent UI — goes outside. Only the "page content" area goes inside Routes. When the route changes, React replaces whatever's inside Routes but leaves everything outside untouched.
The three components you must import from react-router-dom:
BrowserRouter — wraps the whole app in main.jsx, enables routing context
Routes + Route — define the URL map inside App.jsx
Link — replaces anchor tags for navigation without reload

N1
What is Node.js + the V8 Engine
Concept — no file

JavaScript was designed to run inside browsers. Every browser has a JS engine — Chrome uses V8, Firefox uses SpiderMonkey, Safari uses JavaScriptCore. The V8 engine is what actually executes your JavaScript code — it compiles it to machine code and runs it.

Node.js took Google's V8 engine and ripped it out of the browser. Then it added extra capabilities — file system access, network access, the ability to create HTTP servers — things browsers can't do for security reasons. The result: you can now run JavaScript on a server, on your laptop, anywhere — without a browser. Same language, new environment.

concept — Browser JS vs Node.js JS
// In the browser — JS CAN do:
document.getElementById('btn').click()   // manipulate HTML
window.location.href = '/about'           // navigate pages
fetch('https://api.com')                   // make HTTP requests

// In the browser — JS CANNOT do:
const fs = require('fs')   // ❌ no file system access (security)

// In Node.js — JS CAN do:
const fs = require('fs')
fs.readFileSync('file.txt')               // ✅ read files from disk

// In Node.js — JS CANNOT do:
document.querySelector('h1')             // ❌ no DOM (no browser)
window.alert('hi')                       // ❌ no window object
The mental model: V8 is the engine (the JS execution core). The browser is one environment that uses V8. Node.js is another environment that also uses V8. Same JavaScript language — different APIs available depending on where you run it. console.log() works in both. document only exists in the browser. fs only exists in Node.
V8 Engine

Google's JS engine written in C++. Compiles JavaScript directly to machine code. Used by both Chrome and Node.js. Responsible for making JS fast.

Browser environment

V8 + DOM APIs + Web APIs (fetch, localStorage, window, document). Sandboxed — can't touch your filesystem.

Node.js environment

V8 + Node APIs (fs, http, path, process). No DOM. Full system access. Used to build servers, CLIs, scripts.

Built-in Modules — fs and http
Node.js core modules · no install needed

Node.js comes with a set of built-in modules — they're included with Node itself, no npm install required. You require them by name. You covered two of the most important ones: fs (file system) and http (create HTTP servers).

concept — fs module (file system)
const fs = require('fs')   // built-in, no npm install

// Read a file synchronously (blocks until done)
const data = fs.readFileSync('hello.txt', 'utf8')
console.log(data)   // prints file contents

// Write a file
fs.writeFileSync('output.txt', 'Hello from Node!')

// Append to a file
fs.appendFileSync('log.txt', 'New log entry\n')
concept — http module (create a raw HTTP server)
const http = require('http')   // built-in

// createServer takes a callback that runs for EVERY request
const server = http.createServer((req, res) => {
  // req = incoming request (URL, method, headers, body)
  // res = outgoing response (what you send back)

  res.writeHead(200, { 'Content-Type': 'text/plain' })
  res.end('Hello from Node!')
})

server.listen(3000, () => {
  console.log('Server running on port 3000')
})
// Open browser → http://localhost:3000 → sees "Hello from Node!"
Why did you learn the raw http module if you then used Express? Because Express is built on top of the http module. Understanding what Express does underneath — creating a server, listening on a port, receiving requests and sending responses — makes you understand why Express exists and what problem it solves. Express is just a layer of convenience on top of what you just coded.
require() vs import: Node.js traditionally uses require() (CommonJS module system). React/Vite uses import (ES Modules). Both are ways to load code — different systems. In your package.json for the backend, you have "type": "commonjs" — that's why require() works in app.js. Your React frontend uses import because Vite uses ES Modules.
N3
npm, package.json, package-lock.json
package.json · package-lock.json

npm (Node Package Manager) is the registry and tool for installing third-party packages. When you run npm init, it creates package.json — the configuration file that describes your project: its name, version, start script, and most importantly the list of packages it depends on. Every package you install with npm install gets recorded here.

package.json — your actual backend config
{
  "name":        "ecommercebackend",
  "version":     "1.0.0",
  "main":        "app.js",          // entry point — node runs this file

  "scripts": {
    "dev": "node app.js"            // npm run dev → runs node app.js
  },

  "type": "commonjs",               // use require() not import

  "dependencies": {
    "cors":            "^2.8.6",   // allow cross-origin requests
    "express":         "^5.2.1",   // web server framework
    "react-router-dom": "^7.16.0"  // (this is a mistake — belongs in frontend)
  }
}
concept — package.json vs package-lock.json
// package.json — what YOU write and maintain
// "express": "^5.2.1"  means "version 5.2.1 or any compatible higher version"
// The ^ means flexible — npm can install 5.2.5, 5.3.0, etc.

// package-lock.json — what npm GENERATES automatically
// Records the EXACT version of every package + every sub-dependency installed
// "express": "5.2.1" — no ^, no flexibility, locked to exact version
// "has-flag": "4.0.0" — sub-dependency of a sub-dependency, also locked

// WHY the lock file matters:
// You install today → express 5.2.1 installed
// Your teammate installs tomorrow → without lock file, might get express 5.3.0
// With lock file → both of you get exactly 5.2.1, guaranteed identical setup
Key npm commands:
npm init -y — creates package.json with defaults (skip the questions)
npm install express — installs express, adds it to dependencies, creates/updates lock file
npm install — installs everything listed in package.json (what teammates run after cloning)
npm run dev — runs the "dev" script from package.json → node app.js
node_modules is NOT committed to git. It contains thousands of files and is huge. Your package.json and package-lock.json are committed instead. Anyone who clones your repo runs npm install and npm recreates node_modules exactly. That's the contract these two files create.
N4
Express.js — Building the Server
app.js — top section

Express.js is a minimal web framework for Node.js. It wraps the raw http module you saw earlier and adds a much cleaner API for defining routes, handling requests, sending responses, and plugging in middleware. Every real Node.js backend you encounter will use Express or something built on top of it.

app.js — express server setup (top of your actual file)
const express = require('express')   // import express package
const cors    = require('cors')      // import cors package
const app     = express()           // create the app instance
const port    = 3000

app.use(cors())             // middleware: allow requests from other origins
app.use(express.json())    // middleware: parse JSON bodies on incoming requests

// ...

app.listen(port, () => {
  console.log(`the server is running on ${port}`)
  // server is now listening for requests at http://localhost:3000
})
What is CORS and why do you need it? Browsers have a security rule: a web page at http://localhost:5173 (your React app) is not allowed to make requests to http://localhost:3000 (your Node server) unless the server explicitly says it's OK. This is called the Same-Origin Policy. The cors package adds a response header (Access-Control-Allow-Origin: *) that tells the browser "yes, this server allows requests from other origins." Without it, your React fetch calls would fail with a CORS error in the console.
What is middleware? app.use() registers middleware — functions that run on every incoming request before it reaches your route handlers. cors() adds the CORS header to every response. express.json() reads the request body and parses it from a raw string into a JavaScript object, so you can do req.body.title instead of parsing JSON manually. Order matters — middleware runs top to bottom.
Raw http module (verbose)
const http = require('http')
const server = http.createServer((req, res) => {
  if (req.url === '/products'
      && req.method === 'GET') {
    res.writeHead(200, {'Content-Type':'application/json'})
    res.end(JSON.stringify(products))
  }
  // imagine handling 20 routes like this...

server.listen(3000)
Express (clean)
const express = require('express')
const app = express()

app.get('/products', (req, res) => {
  res.json(products)
  // that's it. Express handles Content-Type,
  // JSON.stringify, status 200 automatically
})

app.listen(3000)

app.get + app.post — Your REST API
app.js — GET /products + POST /products

HTTP has different request methods that carry meaning about what the client wants to do. GET means "give me data" — used to retrieve resources, no body needed. POST means "I'm sending you new data" — used to create resources, body contains the new data. Express gives you app.get() and app.post() methods that match exactly those HTTP methods.

app.js — GET /products — send the products array as JSON
// The products array — 20 items, same shape as FakeStore API
let products = [
  { id: 1, title: "Fjallraven Backpack", price: 109.95, image: "...", ... },
  { id: 2, title: "Mens Casual T-Shirt", price: 22.3,  image: "...", ... },
  // ... 18 more
]

// GET /products — when the browser or React fetch() calls this URL
app.get('/products', (req, res) => {
  res.json(products)
  // res.json() → serializes the array to JSON string
  // → sets Content-Type: application/json automatically
  // → sends HTTP status 200 automatically
})

// This is exactly what Products.jsx fetches:
// fetch('http://localhost:3000/products') → hits this route → gets the array
app.js — POST /products — add a new product to the array
// POST /products — when someone sends a new product in the request body
app.post('/products', (req, res) =>  {
  // req.body is the parsed JSON from the request body
  // (only works because of app.use(express.json()) at the top)
  const { id, title, image, price } = req.body

  let newproduct = { id, title, image, price }
  products.push(newproduct)   // adds to the in-memory array

  res.json({ "msg": "products are added successfully" })
  // sends confirmation back to whoever made the POST request
})
concept — how you would test the POST route (from frontend or Postman)
// From the browser / React — fetch with method POST
fetch('http://localhost:3000/products', {
  method:  'POST',
  headers: { 'Content-Type': 'application/json' },
  body:    JSON.stringify({
    id:    21,
    title: "New Product",
    price: 49.99,
    image: "https://..."
  })
})
  .then(r => r.json())
  .then(data => console.log(data))
  // → { msg: "products are added successfully" }

// Then fetch GET /products again → new product is in the list
Important limitation: The products array is stored in memory (let products = [...]). When you restart the Node server with npm run dev, the array resets to the original 20 items — any products you POSTed are gone. To persist data between restarts you'd need a real database (MongoDB, PostgreSQL, SQLite) or at minimum write to a JSON file using fs.writeFileSync(). This is the next step after this project.
